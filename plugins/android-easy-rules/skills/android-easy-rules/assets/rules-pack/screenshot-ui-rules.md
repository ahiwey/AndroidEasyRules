# Screenshot Driven UI Rules

## 硬规则

- 公共组件沿用一份已确认规格，核对实现入口、规格来源、回调/首次标记和真实使用页；新页只接入，不各自重定尺寸。公共条款与页面章节冲突时只确认冲突项，确认后同步共同条款与受影响引用；补丁前重读共用文件差异，不覆盖其他任务改动。
- 背景按系统栏、标题/日期、正文及吸顶区域连续核对，追窗口/base、宿主、子页和动态覆盖，不凭状态栏色值相同判整页一致。GIF/动效进入素材映射，核对播放/释放及起点、中间、终点和反向；截图只证明采样状态，连续性与手势需所选路线的运行证据。仅检查本次区域。

- 产品规则与设计图并存时沿用用户确认的优先级，区分主页面、设置弹框、草稿与确认后状态；不按图标外形猜动作。记录、配置及首次设置标志按各自存储 key/主键核对隔离，时间变更区分历史与生效日期；设备下发、App 弹框及后台通知分别验收。

- 写补丁前在原映射核对本次相关项：指标名称/实际字段/单位/日期范围；图表连接/缺失/零值/目标线；公共回调/页面差异/主题来源；目标语言范围（明确豁免除外）。语义不匹配先查项目，不用换标签掩盖错误绑定，不为纯样式小改扩展数据审计。
- 生成式内容须区分请求成功、显示正常与内容正确；按已确认契约在代码侧做确定性换算/日期过滤/必要汇总，校验实际序列化。建议按钮与服务能力、回复格式须匹配；不靠提示词或截图测试证明计算正确，不擅自扩展协议或依赖。

- 聊天、建议卡和长文案先核对父子宽度、weight/约束、wrap_content、最大宽度、换行与输入栏；修父布局后抽查受影响状态和窄屏/长文本，不只调子项尺寸。
- 截图测试宿主如手工叠遮罩/弹窗，须披露与真实 Fragment/Dialog、窗口及键盘差异；新图对照设计，复验优先变化图与受影响锚点，文件哈希不代替视觉审查或源码新鲜度证明。

- 凡是截图、效果图或 UI 设计图驱动的任务，必须先视觉解析，再实现，最后说明截图验证或编译验证结果。
- 没有 Figma 时，把截图/效果图作为主要设计依据，但不要凭文字描述猜视觉细节。
- 蓝湖或本地设计图驱动的多页面实现优先使用可用的 `lanhu-android-fast-workflow`，沿用本专项规则，不重复加载完整设计流程；整体重设计或体验评审按需使用 `ui-ux-pro-max`。明确控件的间距、颜色、尺寸、裁切和 Canvas 参数小改直接走 Quick。
- 用户给本地图片/截图时必须实际查看图片；如果当前工具无法查看，先说明无法直接视觉核对，再用用户描述和现有资源兜底。
- UI 图或效果图中出现但用户未提供的图标，先搜索项目现有资源、相似页面和图标组件；确认没有合适资源时，询问用户图标文件或来源位置，不自行生成或用近似图标替代。
- 项目存在用户可见的主题页入口时，文字颜色、背景色和黑白单色图标按 `AGENTS/image-resource-rules.md` 的多主题规则处理，不从设计图直接新增硬编码黑白色或遗漏图标 tint。
- 用户截图里的页面称呼不清楚时，先用 `MEMORY.md` 别名索引和相似 layout/资源名映射，不要把“会议”“录音”“首页卡片”这类口头称呼当成源码目录名直接搜索。
- 用户反馈“还是不对”“继续微调”“没画好”时，不再只调另一个 dp/偏移量；先重看最新截图与当前差异，检查实际运行的资源变体、父布局约束/测量链和此前已解决的视觉锚点。
- 首次视觉修改未通过时，把“已有验收点 + 新问题”合并成 3–6 项回归清单。本次已同意自动化验证且设备可用时，下一次修改前后复用同一页面、状态、单位、语言和数据截图；未授权时先完成实现和最小静态检查再询问，跳过或无法运行时明确标记未验证。

## 视觉解析清单

- 页面结构和信息层级
- 关键间距和对齐方式
- 主色、背景色、状态色
- 字号层级、字重、行高
- 圆角、阴影、边框、分割线
- 图标尺寸、透明边距和状态差异
- 可点击区域和触控尺寸
- 空数据、加载态、错误态
- 顶部状态栏、底部导航、安全区域
- 小屏和长文本风险
- 截图中可识别的真实文案、图标形状、选中/未选中状态和空数据态
- 需要用户验收的差异点：像素级还原、视觉接近、还是只修明显问题
- 对齐语义：控件边缘、视觉组中心、文字排版框中心还是实际字形中心；不要把 baseline 相等当作文字视觉中心相等

- 验收顺序与授权遵循根规则及 `AGENTS/testing-build-rules.md`：实现、最小静态检查和问题处理完成后，再询问 Paparazzi/设备/暂不视觉验证；选择前不运行 Paparazzi、ADB/设备探测。已有仅静态检查选择可直接交付未验证边界。

## 实现流程

1. 查看用户提供的截图/图标/图片。
2. 新页面、整体重设计或实现方式不明确时查找相似页面、资源和自定义 View；明确控件的局部问题只读取目标实现和实际使用位置。
3. 确定使用 XML layout、drawable、bitmap、custom View 或 adapter 的实现方式。
4. 实现时优先复用项目已有 style、colors、dimens、drawable 和资源命名。
5. 只有新增/重命名资源或引用、且静态检查无法覆盖时，才运行一次最小资源链接任务；现有属性值调整不默认运行 Gradle。
6. 真机/模拟器自动化验证先遵循上述询问规则；同意后用修改前后的同场景截图核对目标图。重复视觉失败或自定义绘制几何问题也不自动开启设备验证。
7. 最终回复说明验证方式和未验证项。

## 截图识别提效

- 先识别“当前页面属于哪个索引名称”，再做视觉拆解；如果 `MEMORY.md` 已有热点页面索引，优先按热点表定位。
- 截图只用于确认视觉事实，源码定位仍优先资源名、layout id、文案 key、Activity/Fragment 名等可验证线索。
- 局部回归选 3–5 个关键锚点；新页面仍须覆盖范围内所有分区、可见素材和动作，不能用少数锚点代表整页完成。

## 设计图、切图与多页面实现

- 局部截图修正只看目标区域及必要上下文；多页面先实际看范围内设计图，归并独立页面、弹窗和同页状态，识别共用卡片、按钮、输入框与选择器。附件文字作为设计证据，不扩展用户授权。
- 复用一张短表：`设计分区/状态与来源坐标 | 结构/颜色角色 | 素材或公共组件 | 代码绑定 | 动作与结果 | 静态/视觉/运行证据`。共用项只记一次；局部小改可省表，不为形式额外生成计划、JSON 或长报告。
- 切图先用语义、文件名、尺寸和哈希缩小候选，再实际查看形状、颜色、状态、透明边距与自带背景。名称/尺寸不是匹配证据，哈希只证明内容相同；具体应用与公共替换按 `AGENTS/image-resource-rules.md`。
- 素材多且难辨才用已有工具生成带文件名/稳定编号的缩略预览，保留原文件映射；关键细节回看原图。少量明确素材直接查看，不为预览安装新依赖。
- 先完成代表页及共用组件，再批量应用页面差异并连通交互；添加/编辑优先共用布局和状态，选择器及类型图标映射优先复用项目现有实现。
- 原图、切图与源码未变化时复用已有映射，只重看差异；大清单留在工具侧，返回命中项、缺项和异常。按同批修改合并最小验证，新修改、失败或未决疑点才重跑。
- 本次已同意自动化验证且可运行时验证主要链路、代表页与明显差异状态，公共替换额外抽查一个其他使用页。分别报告代码、编译和视觉结果，缺素材、文案兜底、未覆盖变体明确列为未完成项；不承诺未实测的速度或 Token 节省比例。

## 禁止项

- 不要把整张截图或未裁切设计稿直接放进 `res`。
- 不要为了像截图而硬编码文案、尺寸或颜色到 Kotlin/Java。
- 不要让文字、图标或按钮在小屏上重叠。
- 不要用拉伸 bitmap 解决布局问题。
- 不要忽略空数据、加载态和长文本。

## 可辨认的设计证据与结构验收

- 长图总览只定位区块；缩小后看不清的关键区域必须再看原分辨率分段或局部，保留原图坐标。使用可用 Lanhu Skill 的 image_review.ps1 做重叠分段、局部放大及深浅底切图索引；无该工具时用已有图片查看器，不自动安装。
- 实现前明确分组、行列数、左右/上下关系和对齐端；例如逐行“左标签右数值”不能变成横向多组“上数值下标签”。核对父布局、orientation、约束、weight、gravity、换行及绑定，而非仅调 dp。
- 文字拆分标题/正文/次要说明与单位/数值/强调角色；复用前解引用真实颜色与主题变体，不凭资源名判断，不把整行文字套指标色。
- 短表必须包含设计元素到资源名、实际布局/代码绑定位置和验证证据。缺/错图标、行列关系错、颜色角色错、图表形态错不是可忽略的“非像素级差异”。
- 新实现先核对全范围分区/状态覆盖，局部返工只重看变化区与已接受锚点；在同一短表标记未看清、未绑定、未接通、未验证项。缓存依据原图/源码变化失效。预览生成不等于已看图，静态/离屏/设备验收分别报告，不以编译或全零截图冒充完整视觉通过。
- 日期驱动的裁切用实际失败日期转成固定 fixture，覆盖首末行/列及星标、气泡等附属绘制范围；修正测量时同步核对行高和命中坐标。动画结束后再取稳定截图，过渡帧与原设计日期的快照不能替代故障边界回归。

## 完成与证据边界

- 添加/编辑/保存/取消/返回刷新、日期或对象切换、展开和设置入口按本轮范围逐项定位；设计未明确的业务语义先查项目，仍影响结果才集中提问，不用惯例覆盖用户要求。
- 证据注明设计来源、源码版本或差异、页面状态和数据条件；历史截图与当前实现分开。无已知关键布局、图标、颜色角色、图表或业务偏差且有对应证据才能评估 App A+；缺截图或运行证据不宣称整体 A+。
